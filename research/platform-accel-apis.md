# GitHub/GitLab 可用于加速检索的 API 及限制

Ticket: zibyn/gitfar#6 (map: #1). 调研日期 2026-10-27。所有结论引自官方文档（docs.github.com、docs.gitlab.com、git-scm.com）。

## 背景约束（来自 #1）

- git 协议为核心；平台 API 只做**可选加速**（如 fetch 完成前先回答首个查询）。
- 结果必须绑定**精确提交 SHA**，且与 git 数据精确一致。

因此判断每个 API 的关键问题是：**能否钉在一个 commit SHA 上、返回的是否是该 SHA 下的原始 git 数据、是否会截断/过滤**。

## 结论速览

| 原语 | GitHub | GitLab | 是否值得用作加速 |
|---|---|---|---|
| 文件列表 / tree | Git Trees `recursive`（接受 SHA） | Repository tree `recursive`（分页） | **是**（GitHub 首选；须处理 `truncated`）|
| 读文件 | Contents（raw 媒体类型）/ Git Blobs | Raw blob by SHA / Files raw | **是**（按 blob SHA 读最稳）|
| 代码搜索 | REST `search/code`（legacy） | Search API `blobs` / exact code search | **否**（仅默认分支、索引滞后、过滤文件、限额极低）|
| 路径历史 / commits | List commits `path`+`sha` | List commits `path`+`ref_name` | 可选（仅作首屏；与 `git log` 语义不完全相同）|
| compare / diff | Compare（≤250 commits、≤300 files） | Compare（可能 `compare_timeout`、`too_large`）| 否（截断多，本地 diff 更可靠）|
| blame | GraphQL `Commit.blame(path)` | Files blame（`range`） | 可选（首屏；需接受平台算法差异）|
| 归档下载 | tarball/zipball（git archive） | Repository archive（5 req/min on GitLab.com）| **否**（受 `export-ignore`/`export-subst` 影响，不等于 tree）|

一句话：**只用"按 SHA 读 tree/blob"这类与 git 对象一一对应的端点做加速；代码搜索、archive、compare 不用；commits/blame 最多作为 fetch 完成前的临时答案并标注来源。**

## GitHub

### Git Trees API — `GET /repos/{o}/{r}/git/trees/{tree_sha}?recursive=1`

- `tree_sha` 为 "The SHA1 value or ref (branch or tag) name of the tree"。可直接传 commit SHA 解析出的 tree。 [1]
- 上限："The limit for the tree array is 100,000 entries with a maximum size of 7 MB when using the recursive parameter"；超出时 `truncated: true`，需改为逐个子树非递归获取。 [1]
- 返回的是 git tree 对象条目（path/mode/type/sha/size），**与 git 数据精确一致**（就是对象本身）。
- 评价：**最有价值的加速端点**。Linux 内核量级（~9 万文件）接近 10 万上限，必须实现 `truncated` 回退。

### Contents API — `GET /repos/{o}/{r}/contents/{path}?ref=`

- `ref`："The name of the commit/branch/tag. Default: the repository's default branch"。 [2]
- 大小：≤1 MB 全功能；1–100 MB 仅 `raw`/`object` 媒体类型；>100 MB 不支持。 [2]
- 目录列举上限 1,000 个文件，超过需用 Trees API。 [2]
- `application/vnd.github.raw+json` 返回原始字节。按 SHA 读即精确。
- Git LFS 文件返回的是指针（git 中存的就是指针，所以与 git 数据一致）。

### Git Blobs API — `GET /repos/{o}/{r}/git/blobs/{file_sha}`

- 按 blob SHA 取对象，内容由 SHA 寻址，天然精确；配合 Trees API 的 `sha` 使用。（同属 Git database API，见 [1] 所在章节。）

### GraphQL：Blob / Blame

- `Blob.text`："UTF8 text data or null if the Blob is binary"；`isTruncated`："Indicates whether the contents is truncated"。**会截断、二进制返回 null，不宜用于精确读文件。** [3]
- `Commit.blame(path)` → `Blame.ranges[]`，每段含 `startingLine`、`endingLine`、`commit`、`age`(1–10)。 [3][4]
- blame 可钉在指定 commit（在 `object(oid:)` 下的 Commit 上调用），但文档未说明其算法参数（rename/copy 检测、`-w` 等），**不保证与 `git blame` 逐行一致**。
- GraphQL 限额：5,000 points/小时/用户；单次 ≤500,000 节点；>10 秒终止；secondary 2,000 points/分钟；`first/last` 1–100。 [5]

### Code search — `GET /search/code`

- "This endpoint requires you to authenticate and limits you to 10 requests per minute." [6]
- "Only the default branch is considered."；"Only files smaller than 384 KB are searchable." [6]
- 每页 ≤100，全局每次搜索最多 1,000 条结果；查询 ≤256 字符、≤5 个 AND/OR/NOT。 [6]
- REST 端点使用 **legacy** 代码搜索语法（"You only need to use the legacy code search syntax if you are using the code search API"）；fork 仅在 star 多于父仓时被索引。 [7] 文档未说明 legacy 支持正则。
- 新代码搜索（支持正则、符号搜索）同样 "only support searching for code on the default branch"，排除 >350 KiB、vendored/generated、二进制，行 >1,024 字符截断，结果限 100 条；**文档未提供其 API**。 [8]
- 评价：**不可用作加速**。无法指定 SHA、索引与分支头存在滞后、静默排除文件 → 违反"结果绑定精确 SHA 且完整"。顶多作为"提示去哪里找"的非权威信号，v1 不建议。

### Commits / Compare

- List commits：`sha` 为 "SHA or branch to start listing commits from"，支持 `path` 过滤，`per_page` ≤100。 [9]
- Compare `BASE...HEAD`：不分页时 ≤250 commits；changed files ≤300（仅首页）。Get a commit：文件最多 3,000，大 diff 可能 5xx 超时。 [9]
- `path` 过滤的历史语义与 `git log -- path`（history simplification、无 `--follow`）不能从文档确认等价。
- 评价：commits 列表可作为首屏临时结果；compare **不用**（截断严重，本地 diff 更便宜可靠）。

### Archive — tarball / zipball

- 302 重定向到下载 URL；私有仓链接 5 分钟过期。 [2]
- "These snapshots are generated by the git archive command"；同一 commit 的文件内容稳定，但压缩字节布局可能变化。 [10]
- `git archive` 会应用 `.gitattributes` 的 `export-ignore`（不打包）和 `export-subst`（替换占位符）。 [11] → **内容 ≠ 该 SHA 的 tree**；且无 git 对象 SHA、无历史。
- 评价：**不用**。冷启动想要全量文件时应直接走 git 浅克隆/partial clone，数据既精确又可复用。

### 限额与认证（REST）

- 未认证 60/小时/IP；认证用户 5,000/小时；GitHub App 安装 5,000 起、最高 12,500（GHEC 15,000）。 [12]
- Secondary：并发 ≤100（REST+GraphQL 共享）；REST 900 points/分钟（读 1 点）；CPU 90s/60s。 [12]
- 条件请求：带 `If-None-Match`，返回 304 时**不计入**主限额（需带 Authorization）。官方建议串行请求以避免 secondary 限额。 [13]
- 认证：PAT（含 fine-grained）、GitHub App 安装令牌。对自托管单组织服务，**GitHub App** 限额最高、可按仓库授权，契合 #1 的"管理员按 host/前缀配置凭证"。

## GitLab

### Repository tree — `GET /projects/:id/repository/tree`

- `recursive=true`；`ref` 为分支或 tag（缺省为默认分支）；支持 `pagination=keyset` + `page_token`。 [14]
- `per_page` 最大 100。 [15] 内核量级需 ~900 次分页请求 → 首屏加速价值有限，但数据是 tree 条目（含 blob `id`），精确。
- 注：文档对 `ref` 只写 branch/tag；传 commit SHA 能否工作需实测（未验证）。

### 读文件

- Raw blob by SHA：`GET /projects/:id/repository/blobs/:sha/raw` 返回原始字节；普通 blob 端点会把部分非 UTF-8 文本转为 UTF-8，**要精确必须用 raw**。>10 MB blob 限 5 req/min。 [14]
- Files API：`ref` 必填，`content` 为 Base64；raw 端点 `lfs=true` 可取 LFS 实体（默认返回指针）。>10 MB 限 5 req/min。 [16]

### Blame — `GET /projects/:id/repository/files/:path/blame?ref=`

- `ref` 必填；`range[start]`/`range[end]` 限定行区间；400 req/分钟/用户/项目。 [16]
- 与 GitHub 同理：算法参数未文档化，不保证与 `git blame` 一致。

### Search API — `scope=blobs`

- `blobs` 需 Premium/Ultimate；全局/组级仅在 advanced search 或 exact code search 启用时可用。项目级支持 `ref`（branch/tag）。返回 `data` 片段、`path`、`startline`、`ref`。 [17]
- Exact code search（Zoekt）：支持正则；"You can use exact code search only on the default branch of a project"；只索引 <1 MB 且 <20,000 trigram 的文件；自管实例需管理员部署 Zoekt。 [18]
- GitLab.com Search API 100 req/分钟（per IP / per user）。 [19]
- 评价：**不用**。层级付费、依赖实例配置、默认分支限定、文件过滤、返回片段而非完整匹配集 → 无法满足精确等价。

### Commits / Compare / Archive

- List commits：`ref_name`（分支/tag/修订范围）、`path`、`follow`（默认 true，跨重命名）、`first_parent`；不返回 `x-total` 头。 [20]
- Compare：`from`/`to` 接受 SHA 或分支；`compare_timeout: true` 时 `diffs` 可能不完整；`too_large` 的文件 diff 无法获取。 [14]
- Archive：`sha` 接受 tag/分支/commit SHA，可用 `path` 限子目录；GitLab.com 5 req/min。 [14] 同样基于 git archive 语义（`export-ignore`/`export-subst` [11]）。
- 评价：commits 可作首屏；compare、archive **不用**。

### 限额与认证（GitLab.com）

- 认证 API 2,000 req/分钟/用户；未认证 500/分钟/IP；raw 端点 300/分钟（每项目+commit+路径）；Files API 500/分钟（每 IP+路径）；Git over HTTPS 认证 10,000/分钟。 [19]
- 文档列出拟推行的按套餐限额（Free 100/分钟、5,000/小时），尚未生效，届时取较低者。 [19] → GitLab.com Free 场景下 API 加速空间会显著收窄。
- 自管实例：上述限额由管理员配置，不可假设。
- 认证：`PRIVATE-TOKEN` 头（PAT / project / group access token）。 [15]

## 对 gitfar v1 的建议

1. **值得做（若做加速）**：GitHub Trees（recursive）+ Blobs/Contents raw，按**已解析的 commit SHA** 调用。数据是 git 对象本身，可与后续 fetch 结果直接对账（blob SHA 相同即一致）。GitLab 对应 tree + `blobs/:sha/raw`，但分页成本高，收益次之。
2. **可选、标注为临时**：commits 路径历史、blame。返回时须携带 SHA 并标明"platform-sourced"，fetch 完成后以本地 git 结果为准。
3. **不做**：两平台的代码搜索（默认分支、过滤、限额、无 SHA 绑定）、archive（`export-*` 改写内容）、compare（截断）。
4. 首屏的"ref → SHA"解析本身用 git `ls-remote` 即可，无需 API。
5. 加速路径必须容忍 secondary 限额/429，失败即回退 git，不阻塞主路径；使用条件请求（GitHub ETag/304 不计主限额）。
6. 平台 API 加速是否进入 v1，取决于 #1 下"存储与执行"相关调研得出的冷 fetch 耗时：若 partial clone（`--filter=blob:none`）+ 按需取 blob 已足够快，API 加速的边际价值很低，可推迟。

## 未验证 / 风险

- GitLab tree/files 的 `ref` 传 commit SHA 的行为（文档只写 branch/tag）。
- 平台 blame / path-history 与 `git blame` / `git log -- path` 的逐行等价性（文档未说明算法）。
- raw.githubusercontent.com 的限额（非 REST 文档范围，未调研）。
