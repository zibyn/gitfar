# gitfar v1 设计规格

本文件是 gitfar v1 的规范性设计。它由地图 [gitfar v1：像检索本地一样检索远程 git 仓库](https://github.com/zibyn/gitfar/issues/1) 上各决策工单的结论组装而成，每节末尾标注来源。合并后，本文件与来源工单冲突时以本文件为准。术语以 [`GLOSSARY.md`](../../GLOSSARY.md) 为准，关键决策见 [`docs/adr/`](../adr/)。

标注 **〔补〕** 的条目是起草时发现的空白，工单里没有明确结论，由本文件首次规定。

## 1. 概述

gitfar 是自托管、单组织使用的只读远程代码检索服务。**服务端** `gitfard` 拉取并缓存**远程仓库**，执行**检索原语**；**客户端**（CLI `gitfar` 或任意远程 MCP 客户端）只调用服务端，用户本地不克隆仓库。

设计目标：

- 原语形状模仿智能体最常用的本地命令（`sed -n`、`grep/rg -n`、`ls/find`、`git log/show/diff/blame`），结果与本地 git 精确一致。
- 每个结果都带**解析提交**；按 SHA 的结果永久可复现，分支按 TTL 刷新。
- 规模：Linux 内核量级仓库、数十并发请求，单实例。

### 1.1 请求生命周期

```
客户端 ──Bearer──▶ ① 鉴权 ─▶ ② 解析参数/游标 ─▶ ③ 规范化 URL ─▶ ④ 授权
                                                                       │
   ⑨ 响应 + 请求日志 ◀─ ⑧ 截断/游标 ◀─ ⑦ 执行 ◀─ ⑥ 解析 rev ◀─ ⑤ 缓存
```

1. **鉴权**：校验 `Authorization: Bearer <客户端访问令牌>`，失败返回 401 `unauthenticated`（§4.2）。
2. **解析参数**：校验原语参数；若只带 `cursor`，从游标解码出原始请求、解析提交和偏移（§2.4）。
3. **规范化**：把 `repo` 归一化为**规范 URL**（§4.3）。
4. **授权**：允许列表 × 令牌范围 × （存在匹配仓库凭证 或 公开仓库），不看缓存状态；不通过返回 `not_found`（§4.4，[ADR 0001](../adr/0001-authorization-independent-of-cache.md)）。
5. **缓存**：命中负缓存返回 `not_found`；仓库被标记为凭证失效返回 `upstream_unavailable`；未缓存则触发**预热**，最多等约 20 s，超时返回 `repo_warming`；分支 TTL 过期则做 singleflight 前台 fetch，约 5 s 超时后用旧 SHA（§4.5）。
6. **解析 rev**：持仓库读锁，在服务端 ref 镜像中把 `rev` 解析成完整 SHA；整个请求锁定在该 SHA 上（续读请求直接使用游标中的 SHA）。
7. **执行**：read/list/grep 走进程内 gix，log/show/blame 走 git CLI（§4.6）。截止时间约 30 s。
8. **截断**：超出条数上限、字节硬顶或截止时间时截断，生成**续读游标**。
9. **响应**：返回原语响应对象；记一行请求日志（§6.4）。

## 2. 检索原语

v1 共 6 个原语：`read`、`grep`、`list`、`log`、`show`、`blame`。

### 2.1 通用参数

- `repo`（必填）：任意形式的仓库 URL（`https://…`、`git@host:path`、`host/path`），服务端归一化为规范 URL。
- `rev`（可选）：任意 git revision 表达式，由 git 解析；默认 `HEAD`，即上游默认分支。
- 服务端无状态：没有会话、没有"当前仓库"。客户端需要多次调用间的一致性时，把上次响应的 `resolved_commit` 作为 `rev` 传回；服务端不做隐式锁定。

### 2.2 响应对象

所有原语返回同一形状：

```json
{
  "text": "…模仿本地命令输出的文本主体…",
  "resolved_commit": "<40 位 SHA>",
  "truncated": true,
  "truncated_reason": "limit",
  "next": "<续读游标>",
  "...": "原语特有元数据"
}
```

- `truncated_reason` 〔补〕：`limit`（达到条数/行数上限）、`bytes`（达到字节硬顶）、`deadline`（达到截止时间）。未截断时 `truncated=false`，不带 `truncated_reason` 和 `next`。
- 总输出字节硬顶约 64 KB（`text` 的 UTF-8 字节数）。
- 短 SHA 固定 12 位；日期为 ISO 8601 日期部分（`2026-10-27`）。

### 2.3 各原语

| 原语 | 参数 | 输出与规则 |
|---|---|---|
| `read` | `repo, rev?, path, start_line?, end_line?` | `cat -n` 风格行号。默认 200 行，硬上限 2000 行。元数据带 `total_lines`。二进制文件只返回元数据 `binary: true, size`，`text` 为空。目录返回错误 `is_directory`。symlink 返回链接目标文本，不跟随。`rev:path` 形式的读取统一走这里 |
| `grep` | `repo, rev?, pattern, path[]?, include[]?, exclude[]?, fixed_string?, ignore_case?, before?, after?, context?, output_mode?: lines\|files\|count（默认 lines）, max_results?, skip_large?（默认 true）` | Rust `regex` 语法：无回溯、无多行匹配。`lines`：`path:line:text`，上下文行 `path-line-text`，组间 `--`。`files`：每行一个路径。`count`：`path:N`。默认 100 条匹配；单行截断到约 500 字符。跳过二进制文件。结果严格按路径字典序 + 行号排列，保证游标稳定。默认跳过大于 10 MB 的 blob 并列入元数据 `skipped_large`；`skip_large=false` 时不跳过。不进入 submodule |
| `list` | `repo, rev?, path?, glob?, max_depth?（默认 1）, type?: file\|dir\|any（默认 any）` | 覆盖 `ls` 与 `find`。每行一个相对仓库根的路径，目录以 `/` 结尾，submodule 显示为 `path@ <sha12>`。默认上限 1000 条。不输出 size、mode。不进入 submodule |
| `log` | `repo, rev?, path[]?, max_count?（默认 20）, since?, until?, author?, grep?` | 每个提交一行 `<sha12> <date> <author> <subject>`。不支持 `-p`、`--follow` |
| `show` | `repo, rev（必填：单个 rev 或 a..b 区间）, path[]?, format?: stat\|name-only\|patch（默认 patch）, context_lines?（默认 3）` | 单个 rev：先输出提交头再输出 diff；区间：只输出 diff。兼任 `diff`。patch 文本与 git 一致，按字节截断，可用游标续读 |
| `blame` | `repo, rev?, path, start_line, end_line`（行区间必填，最多 500 行） | 每行 `<sha12> <author> <date> <line>) <text>` |

`include`/`exclude`/`glob` 使用 git pathspec 风格的 glob（`*` 不跨 `/`，`**` 跨目录）〔补〕。`path[]` 是相对仓库根的路径前缀。

### 2.4 截断与续读游标

- 每个原语有默认上限与可调上限（见上表），另受字节硬顶约束。超出时返回 `truncated=true` 与不透明游标 `next`。
- 游标编码"原始请求 + 解析提交 + 偏移"，服务端不保存任何状态；续读一定落在同一个 SHA 上。详见 [ADR 0004](../adr/0004-stateless-cursor-pinned-to-sha.md)。
- 续读请求**只**传 `{cursor}`；与其他参数同传返回 `invalid_argument`。
- 续读请求照常经过鉴权与授权（§1.1 ①–④）；令牌被吊销或配置收紧后，旧游标随即失效。
- 游标格式〔补〕：`base64url(版本字节 ‖ 紧凑序列化的 {原语, 参数, resolved_commit, 偏移})`，不签名（授权每次重做，伪造游标只能构造调用方本来就能发起的请求）。服务端无法解码或版本不支持时返回 `invalid_argument`。
- grep 在截止时间到达时返回已完成的有序前缀 + 游标，`truncated_reason=deadline`。

### 2.5 错误码

| 错误码 | HTTP | CLI 退出码 | 含义 |
|---|---|---|---|
| `invalid_argument` | 400 | 2 | 参数非法、游标非法、游标与其他参数同传 |
| `is_directory` | 400 | 2 | `read`/`blame` 的 `path` 是目录 |
| `unauthenticated` | 401 | 4 | 令牌缺失、错误或过期，不区分原因 |
| `not_found` | 404 | 3 | 仓库不存在、无权访问、不在允许列表或令牌范围内，三者不区分 |
| `path_not_found` | 404 | 3 | 已授权仓库内路径不存在 |
| `rev_not_found` | 404 | 3 | 已授权仓库内 rev 无法解析 |
| `repo_warming` | 503 〔补〕 | 5 | 仓库正在预热；可重试，带进度 |
| `cache_full` | 507 〔补〕 | 5 | 空闲磁盘低于硬下限，无法克隆新仓库；需管理员介入 |
| `upstream_unavailable` | 502 | 5 | 仓库被标记为凭证失效，或公开仓库匿名拉取失败（需要配置凭证） |
| `deadline_exceeded` | 504 〔补〕 | 6 | git CLI 原语在截止时间内未产出结果（grep 不会返回此错误，见 §2.4） |
| `internal` | 500 〔补〕 | 6 | 服务端内部错误 |

- 无权访问与不存在统一为 `not_found`，不泄露私有仓库是否存在。只有通过授权后，`path_not_found`/`rev_not_found`/`is_directory`/`upstream_unavailable` 才可区分。
- `repo_warming` 的错误体附带进度 〔补〕：`{"error":{"code":"repo_warming","message":"…","progress":{"state":"queued|cloning|rate_limited","queue_position":3}}}`，HTTP 响应带 `Retry-After`。
- `cache_full` 不可通过重试自愈；CLI 把它归入退出码 5 是按"服务端暂时无法提供"分类，CLI 不会自动重试它。

来源：[检索原语集合与语义](https://github.com/zibyn/gitfar/issues/8)、[客户端协议：HTTP API 与 MCP 工具映射](https://github.com/zibyn/gitfar/issues/10)、[缓存生命周期：预热、淘汰与上游限速](https://github.com/zibyn/gitfar/issues/13)、[服务端存储与检索执行架构](https://github.com/zibyn/gitfar/issues/9)、[从 Claude Code / Codex 对话记录中提炼常用代码检索操作](https://github.com/zibyn/gitfar/issues/2)。

## 3. 客户端协议

HTTP API 与 MCP 端点由同一个 axum 应用在同一个 API 监听地址上提供。HTTP 请求/响应与 MCP 工具参数/`structuredContent` 共用同一组 Rust 类型，schema 由 schemars 一次生成。

### 3.1 HTTP API

- `POST /v1/{read|grep|list|log|show|blame}`：JSON 请求体即 §2.3 的参数（或 `{"cursor": "…"}`），成功返回 200 与 §2.2 的响应对象。
- 错误返回 §2.5 的状态码，响应体统一为 `{"error":{"code":"…","message":"…"}}`。
- `GET /v1/whoami`：返回 `{"token_id": "…", "scope": ["…"] | null}`（`null` 表示全局）。
- `GET /healthz`：不鉴权的存活检查。
- 不提供列出仓库的端点：允许列表是前缀，无法枚举。
- 鉴权：除 `/healthz` 外一律要求 `Authorization: Bearer <客户端访问令牌>`。

### 3.2 MCP

- 端点：`/mcp`，Streamable HTTP，无状态模式（rmcp `NeverSessionManager`、`json_response=true`，不使用旧会话协议）。
- 鉴权：同一个 bearer 中间件，失败在 HTTP 层返回 401；v1 不做 OAuth。
- 必须配置 `allowed_hosts`（rmcp 默认只允许 loopback）与 Origin 校验（MCP spec MUST），取自配置 `[server] public_hosts` / `allowed_origins`。
- 工具：裸名 `read`/`grep`/`list`/`log`/`show`/`blame`，由客户端按服务名加命名空间。每个 description 的第一句写明"检索远程仓库（需 repo 参数），不是本地工作区"。
- 结果：`content` 为 `text` 末尾追加一行固定页脚：截断时 `[resolved_commit=<sha> truncated=true next=<cursor>]`，未截断时 `[resolved_commit=<sha>]`；`structuredContent` 为完整响应对象，并声明 `outputSchema`。这样即使客户端不把 structuredContent 交给模型，模型也能续读。
- 领域错误作为工具结果返回 `isError: true`，文本为 `<code>: <message>`，让模型自行纠正。只有协议层问题（如 401）走 HTTP / JSON-RPC 错误。
- 已确认可接入的客户端：Claude Code（`--transport http --header "Authorization: Bearer …"`）、Codex（`url` + `bearer_token_env_var`）。

### 3.3 演进

`/v1` 内只做加法（新增可选参数和字段）；破坏性变更升 `/v2`。MCP 工具 schema 遵循同样规则，不另设版本号。

来源：[客户端协议：HTTP API 与 MCP 工具映射](https://github.com/zibyn/gitfar/issues/10)、[Rust MCP SDK 对 Streamable HTTP 与认证的支持](https://github.com/zibyn/gitfar/issues/5)。

## 4. 服务端模块

### 4.1 配置与热加载

单个 TOML 文件，`gitfard serve --config <path>` 加载。下面是键的总览〔补：键名为本文件首次规定，语义来自各来源工单〕：

```toml
[server]
listen = "0.0.0.0:8080"          # 重启生效
admin_listen = "127.0.0.1:9090"  # 重启生效
cache_dir = "/var/lib/gitfar"    # 重启生效
public_hosts = ["gitfar.example.com"]   # MCP allowed_hosts
allowed_origins = []                    # MCP Origin 校验
scan_threads = 0                 # 0 = 核数；重启生效
request_deadline = "30s"
log_format = "json"              # json | pretty

[cache]
disk_budget = "500GB"
disk_min_free = "10GB"           # 硬下限，低于即 cache_full
blob_lru = "auto"                # auto = 物理内存 1/4；重启生效
blob_lru_max_object = "8MB"
branch_ttl = "60s"               # 〔补〕默认值
warm_wait = "20s"
fetch_timeout = "5s"
clone_concurrency = 2
maintenance_window = "03:00-05:00"

[upstream]
host_concurrency = 4
cooldown_initial = "30s"
cooldown_max = "15m"
negative_cache_ttl = "5m"

allowlist = ["github.com/acme", "gitlab.example.com/platform"]
warm_list = ["github.com/acme/monorepo"]

[[credentials]]
prefix = "github.com/acme"
token = "env:GITHUB_ACME_TOKEN"  # 字面值 | env:VAR | file:/path

[[client_tokens]]
id = "ci-bot"
hash = "sha256:…"
scope = ["github.com/acme"]      # 可选，缺省为全局
expires_at = "2027-01-01T00:00:00Z"  # 可选
```

- **SIGHUP 热加载**：允许列表、仓库凭证、预热列表、客户端访问令牌、TTL、各项限速参数、磁盘预算、维护窗口、截止时间。监听地址、缓存目录、线程池大小、blob LRU 预算须重启。
- 新配置校验失败时保留旧配置，记一条错误日志。
- 仓库凭证值可写字面值、`env:VAR` 或 `file:/path`。配置文件权限由部署方负责；凭证与令牌原文绝不进日志。

来源：[部署与运维：持久化、扩展与可观测性](https://github.com/zibyn/gitfar/issues/14)、[仓库凭证配置与缓存访问控制模型](https://github.com/zibyn/gitfar/issues/7)（该工单曾定"凭证不支持 `env:`/`file:` 引用"，已被前者推翻）。

### 4.2 客户端访问令牌鉴权

- **签发**：离线子命令 `gitfard token new --id <令牌标识> [--scope <前缀>…] [--expires <RFC3339>]` 生成令牌，原文只打印一次，同时打印一段可粘贴进配置的 `[[client_tokens]]` 条目。管理员粘贴后发 SIGHUP。不做管理 API。
- **格式**：`gfr_` 前缀 + 32 字节随机数（base62）。服务端不从令牌本身解析任何信息。
- **存储**：配置只存 `hash = "sha256:<hex>"`。校验时对请求令牌做 SHA-256 并常量时间比较；不用慢哈希（令牌为高熵随机串）。
- **条目**：`id`（必填且唯一，即**令牌标识**）、`hash`、可选 `scope`（**令牌范围**）、可选 `expires_at`。
- **过期**：每次请求判定 `expires_at`，不依赖热加载。默认永不过期。
- **轮换**：新增条目 → 客户端切换 → 删除旧条目，每步 SIGHUP；并存期间新旧都有效。
- **吊销**：删除条目或把 `expires_at` 设为过去，热加载成功后之后的每个请求（含续读）立即被拒；进行中的请求最多再跑一个截止时间。
- **失败**：缺失、错误、过期一律 401 `unauthenticated`，响应不区分原因，原因只进日志。
- **零令牌**：配置中没有令牌时拒绝所有请求（401），启动与热加载时各记一条警告。无匿名模式。
- **日志/指标**只记令牌标识；不记原文、哈希或哈希前缀。认证失败记 `token=none`。

来源：[客户端访问令牌的签发、轮换与吊销](https://github.com/zibyn/gitfar/issues/15)。

### 4.3 规范 URL

- 统一为 `host/path`：去 scheme 与 userinfo，去尾部 `.git` 与 `/`，host 转小写，path 保留大小写。`git@host:path` 改写为同形，一律按 HTTPS 拉取。
- 前缀匹配（允许列表、令牌范围、仓库凭证、预热列表）只在**路径段边界**生效：`github.com/acme` 匹配 `github.com/acme/x`，不匹配 `github.com/acme-evil`。
- 缓存键 = 规范 URL。

### 4.4 授权与仓库凭证

- **凭证规则**：`[[credentials]]` 列表，按规范 URL **最长前缀**匹配；一个 URL 只对应一份凭证。v1 只支持 HTTPS 静态 token（PAT、GitLab project/group token），经 git CLI 的 `GIT_ASKPASS` 或 `http.extraHeader` 注入，不写入仓库 config。
- **授权判定**（每个请求，先于且独立于缓存，[ADR 0001](../adr/0001-authorization-independent-of-cache.md)）：
  1. 规范 URL 在允许列表内；
  2. 规范 URL 在令牌范围内（全局令牌恒真）；
  3. 存在匹配凭证，或该仓库按公开仓库处理（无匹配凭证时匿名拉取）。
  任一不满足返回 `not_found`。配置收紧立即生效，已缓存数据随即不可读。
- **不按读取回源**：上游撤销凭证的传播延迟以分支 TTL 为上限。刷新 fetch 返回认证失败时，把仓库标记为**凭证失效**并拒绝读取（`upstream_unavailable`）；下一次 fetch 成功（如管理员更新凭证后）清除标记〔补〕。
- **公开仓库**：在允许列表内但无匹配凭证时匿名拉取；匿名拉取认证失败时，对令牌范围内的调用方返回 `upstream_unavailable`，message 提示需要配置凭证。

来源：[仓库凭证配置与缓存访问控制模型](https://github.com/zibyn/gitfar/issues/7)。

### 4.5 仓库缓存

#### 存储布局

- 每个上游一份**完整** bare 克隆（不带 `--filter`），路径 `<cache_dir>/repos/<规范 URL>.git`〔补〕。依据见 [ADR 0002](../adr/0002-full-clone-not-blobless.md)。
- 镜像 `refs/heads/*` 与 `refs/tags/*`〔补〕；不拉平台私有 ref（如 `refs/pull/*`）。`HEAD` 跟随上游默认分支。
- fetch 后固定写 commit-graph（含 Bloom 过滤）。
- 每个仓库目录内有一个 touch 文件，其 mtime 记最近访问时间，重启不丢。
- 进程启动时对缓存目录加文件锁，同一目录只允许一个进程。

#### 预热

- 两种触发：该仓库的首次请求；管理员配置的**预热列表**。
- 预热列表中的仓库在启动时入队，此后按分支 TTL 在后台 fetch 保持新鲜；其余仓库只在有请求时刷新，无人访问不产生上游流量。
- 全局并发克隆上限默认 2，超出 FIFO 排队。
- 首次请求最多等约 20 s（`warm_wait`），超时返回 `repo_warming`，进度区分排队第 N 位 / 克隆中 / 上游限流。
- 克隆写入临时目录，完成后原子 rename。启动时清掉所有临时目录（git clone 不可续传），预热列表里的仓库重新入队，其余等下次请求。

#### 刷新

- 分支 TTL 过期后，同一仓库只跑一次前台 fetch（singleflight），超时约 5 s；超时或失败时用旧 SHA 回答，fetch 在后台继续。结果带解析提交，不会误导。
- SHA 形式的 rev 解析结果永久有效。
- rev 无法解析时〔补〕：若距该仓库上次成功 fetch 已超过 60 s，做一次 singleflight 前台 fetch 后重试解析；仍失败返回 `rev_not_found`。

#### 淘汰

- 单一磁盘预算（字节），按最近访问整仓 LRU **淘汰**，淘汰持该仓写锁。被淘汰仓库下次请求时重新预热。
- 预热列表中的仓库不淘汰；预热列表总量超出预算只记警告。移出列表即变回普通仓库。
- 克隆过程中按需淘汰 LRU 尾部。空闲磁盘低于硬下限时：中止当前克隆并清理残余，暂停排队中的克隆，新的需要克隆的请求返回 `cache_full`。已缓存仓库照常可读。
- 不做按仓库或按 host 的子配额。

#### 上游限速

- 按 host 限 clone + fetch 并发，默认 4；不做令牌桶。
- 遇 429/503 对整个 host 进入**冷却**：有 `Retry-After` 则遵循，否则指数退避 + 抖动（30 s 起，封顶 15 min）。冷却期间跳过到期 fetch、用旧 SHA 回答；新克隆留在队列，请求返回 `repo_warming`（`rate_limited`）。
- **负缓存**：克隆的确定性失败（404、认证失败）在内存中负缓存 5 分钟，期间直接返回 `not_found`。网络错误与 429 不负缓存，走冷却。

#### 维护

- fetch 后若 pack 数 > 16，持写锁执行 `git repack --geometric=2 -d` 并增量写 commit-graph。
- 每日维护窗口内对到期仓库做完整 `git gc`（含 prune），并删除已不在允许列表内的仓库（授权本已独立于缓存，所以配置变更时不同步删除）。

#### 并发一致性

- 每个仓库一把读写锁：读请求与 fetch 持读锁；gc/repack 与淘汰持写锁。
- 请求的 rev 先解析成 SHA，整个请求锁定在该 SHA 上。

来源：[服务端存储与检索执行架构](https://github.com/zibyn/gitfar/issues/9)、[缓存生命周期：预热、淘汰与上游限速](https://github.com/zibyn/gitfar/issues/13)、[Linux 内核规模基准测试](https://github.com/zibyn/gitfar/issues/12)。

### 4.6 检索执行

git 访问采用混合方案，见 [ADR 0003](../adr/0003-git-cli-plus-gix.md)。

| 原语 | 执行器 | 说明 |
|---|---|---|
| `read` | gix | 按 SHA 读 tree/blob |
| `list` | gix | tree 遍历 + glob 过滤 |
| `grep` | gix + grep-searcher | 按文件在 rayon 线程池上并行 `search_slice`，按路径字典序合并输出 |
| `log` | git CLI | 依赖 commit-graph 与 Bloom 过滤 |
| `show` | git CLI | patch 文本须与 git 一致 |
| `blame` | git CLI | `git blame -L` |
| clone / fetch / repack / gc | git CLI | 凭证经 `GIT_ASKPASS`/`http.extraHeader` 注入 |

- **解压缓存**：内存 LRU，键为 blob OID、值为解压后的内容，相邻提交间共享。预算按字节，默认物理内存 1/4；单个 blob > 8 MB 不进缓存（照常读取）。v1 不做磁盘 worktree 快照。
- **并发**：扫描共用一个大小等于核数的 rayon 线程池；git 子进程用信号量限流〔补：默认上限 = 核数〕。v1 只有全局限制，不做按令牌的配额。
- **截止时间**：每个请求约 30 s。grep 到点返回有序前缀 + 游标（`deadline`）；git CLI 原语到点终止子进程并返回 `deadline_exceeded`〔补〕。
- **一致性**：grep 结果须与 `git grep` 对同一提交的结果精确一致（内核实测匹配计数一致）。
- 以后 gix 能力补齐，可以按原语迁移执行器，对外接口不变。

来源：[服务端存储与检索执行架构](https://github.com/zibyn/gitfar/issues/9)、[Rust git 实现选型：gix vs git2 vs git CLI](https://github.com/zibyn/gitfar/issues/3)、[服务端存储与 grep 执行方式对比](https://github.com/zibyn/gitfar/issues/4)、[Linux 内核规模基准测试](https://github.com/zibyn/gitfar/issues/12)。

## 5. CLI（`gitfar`）

- **二进制**：客户端 `gitfar` 独立发布，只依赖 HTTP 客户端，只调 HTTP API；不含服务端子命令。
- **配置**：服务端地址与令牌来自 `GITFAR_URL` / `GITFAR_TOKEN`，或 `$XDG_CONFIG_HOME/gitfar/config.toml`（`url`、`token`）。优先级：命令行 > 环境变量 > 配置文件。`--url` 可覆盖地址；令牌没有命令行参数。v1 不做 `gitfar login`。
- **子命令**：每个原语一个，必填参数用位置参数：

  ```
  gitfar read  <repo> <path>            [--rev R] [--start-line N] [--end-line M]
  gitfar grep  <repo> <pattern> [path…] [--rev R] [-i] [-F] [-l] [-c] [-A N] [-B N] [-C N] [-m N]
                                        [--include G]… [--exclude G]… [--no-skip-large]
  gitfar list  <repo> [path]            [--rev R] [--glob G] [--max-depth N] [--type T]
  gitfar log   <repo> [path…]           [--rev R] [--max-count N] [--since D] [--until D] [--author A] [--grep P]
  gitfar show  <repo> <rev>             [path…] [--format F] [--context-lines N]
  gitfar blame <repo> <path> --start-line N --end-line M [--rev R]
  gitfar whoami
  ```

  长标志与原语参数名一一对应（`start_line` → `--start-line`）。只有 grep 额外提供 GNU grep 短别名 `-i -F -l -c -A -B -C -m`；行号总是输出，没有 `-n`。不支持 `foo/bar` 简写与默认仓库，`<repo>` 原样交给服务端。
- **输出**：默认把 `text` 打印到 stdout；`--json` 时把完整响应对象（或错误体）打印到 stdout，不输出 stderr 页脚。不做颜色和分页器。
- **页脚与续读**：成功调用都在 stderr 打印一行页脚，格式与 MCP 页脚相同。续读用 `gitfar <primitive> --cursor <next>`，可省略位置参数；与其他参数同传报用法错误。
- **`repo_warming`**：默认自动重试，直到总耗时达到 `--wait`（默认 90 s，低于常见智能体 shell 的 120 s 超时），每次重试在 stderr 打印一行进度；超时后以 `repo_warming` 退出。`--wait 0` 不重试。其他错误不自动重试。
- **退出码**：`0` 成功（含截断）；`1` grep 无匹配；`2` 用法错误、`invalid_argument`、`is_directory`；`3` `not_found`、`path_not_found`、`rev_not_found`；`4` `unauthenticated`；`5` `repo_warming`、`upstream_unavailable`、`cache_full`；`6` 网络错误、`deadline_exceeded`、`internal`。stderr 错误统一为 `gitfar: <code>: <message>`。

来源：[CLI 人机交互细节](https://github.com/zibyn/gitfar/issues/16)、[客户端协议：HTTP API 与 MCP 工具映射](https://github.com/zibyn/gitfar/issues/10)。

## 6. 部署与运维

### 6.1 部署形态与持久化

- 单实例，靠加机器配置扩容；缓存目录文件锁防止多进程共用。
- 只持久化**配置文件**与**缓存目录**，不引入数据库。缓存目录必须挂持久卷（可重建，但很慢）。负缓存、冷却状态、blob LRU 只在内存中。
- 不备份。配置文件由管理员纳入版本管理；缓存丢失后预热列表中的仓库在启动时全部重新克隆（文档提醒上游流量高峰）。

### 6.2 打包与入口

- OCI 镜像：只含 `gitfard` 单个 Rust 二进制与版本固定的 git；同时提供裸二进制（`gitfard`、`gitfar`）。
- 启动时检查 git 版本 ≥ 2.33，不满足拒绝启动。
- 只提供明文 HTTP；TLS 交给反向代理或 ingress 终止，文档给出示例。

### 6.3 管理监听地址

与 API 分开，默认 `127.0.0.1`，不鉴权，只读：

- `GET /metrics`（Prometheus）：按原语与错误码分组的请求数和延迟直方图；截断次数（按原因）；克隆队列长度与进行中数量；按 host 的冷却状态与剩余时长；fetch/克隆成败计数；磁盘使用量、预算、空闲量；`cache_full` 状态；淘汰次数；blob LRU 命中率与占用；rayon 线程池与 git 子进程信号量饱和度。
- `GET /status`（JSON）：克隆队列明细（规范 URL、排第几位或正在克隆）、各 host 冷却状态、预热列表是否超出预算、磁盘状况。
- `GET /healthz`：存活检查。
- `GET /readyz`：配置已加载、缓存目录可写、git 可用。上游冷却与 `cache_full` **不**影响就绪（单实例摘流量只会让已缓存仓库也不可读）。
- v1 不做管理写接口。

### 6.4 日志

- `tracing` 结构化日志到 stdout，默认 JSON，可切换为人类可读格式。
- 每个请求一行：原语、规范 URL、请求的 rev、解析提交、耗时、截断原因、领域错误码、令牌标识。
- 克隆、fetch、淘汰、冷却、gc 各自记事件日志。
- 禁止出现仓库凭证与客户端访问令牌原文。

### 6.5 告警

服务端不内置告警，文档给出推荐 Prometheus 规则：`cache_full` 持续存在；任意 host 冷却超过 30 min；预热列表超出磁盘预算；预热列表中的仓库 fetch 连续失败；克隆队列积压；空闲磁盘逼近硬下限。

### 6.6 停机

SIGTERM 后停止接收新请求，进行中的请求最多再跑一个截止时间（约 30 s）。进行中的克隆中止，残留临时目录由下次启动清理。fetch 与 gc 终止 git 子进程。

来源：[部署与运维：持久化、扩展与可观测性](https://github.com/zibyn/gitfar/issues/14)。

## 7. 代码组织与 crate 选型

建议 Cargo workspace 〔补〕：

| crate | 内容 |
|---|---|
| `gitfar-proto` | 原语参数、响应对象、错误码类型（serde + schemars），HTTP 与 MCP 共用，CLI 也依赖它 |

| 用途 | 选型 | 备注 |
|---|---|---|
| git 网络与历史类原语 | git CLI（≥ 2.33，镜像内固定版本） | clone/fetch/repack/gc、log/show/blame |

| 不使用 | `git2` | `Repository` 非 `Sync`，partial clone 不完整 |

| 异步运行时 / HTTP | `tokio`、`axum`、`tower` | |

| schema | `schemars` 1.x | 与 rmcp 宏一致 |

| 日志 | `tracing`、`tracing-subscriber` | |
| 指标 | 〔补〕`prometheus-client` | |
| 令牌校验 | 〔补〕`sha2` + `subtle` | SHA-256 + 常量时间比较 |
| CLI | 〔补〕`clap`、`reqwest`（rustls） | |

## 8. v1 不做

- 远程写操作。
- 向量/语义检索、RAG/Wiki 式预生成内容。
- 本地运行版本（仅托管服务）。
- 多租户 SaaS。
- Issue/PR 等平台元数据检索（见 [后续规划：检索 Issue/PR 等平台元数据作为调研参考](https://github.com/zibyn/gitfar/issues/11)）。
- SSH key、GitHub App 形式的仓库凭证；v1 仅 HTTPS 静态 token。
- 平台 API 加速（GitHub trees/blobs 等）；冷启动靠预热与可重试的 `repo_warming`（调研见 [GitHub/GitLab 可用于加速检索的 API 及限制](https://github.com/zibyn/gitfar/issues/6)）。
- trigram 词法索引；不预留接口。
- 多实例部署（共享缓存或分片）。
- OAuth、管理写接口、按令牌配额、磁盘 worktree 快照、`log -p`/`--follow`、多行正则。
