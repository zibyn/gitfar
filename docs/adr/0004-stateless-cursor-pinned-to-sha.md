# 续读游标无状态，并锁定解析提交

截断结果返回的续读游标是"原始请求 + 解析提交 + 偏移"的编码（`base64url(版本字节 ‖ 紧凑序列化)`），服务端不保存任何分页状态。续读时服务端解码游标、直接在游标里的 SHA 上执行，跳过 rev 解析，所以即使分支在两次调用之间移动，续读也一定落在同一个提交上，拼起来的结果与一次性取完相同。这要求每个原语的输出顺序是确定的（grep 严格按路径字典序 + 行号），偏移才有意义。

游标不签名、不加密，也不绑定令牌：每个续读请求照常完整走鉴权和授权（ADR 0001），伪造游标只能构造调用方本来就能直接发起的请求。令牌吊销或配置收紧后，旧游标随即失效。

后果：服务端可以随意重启、单实例也无需会话存储，MCP 端点可跑无状态模式；游标长度随请求参数增长（但仍远小于 64 KB 的输出硬顶）。如果游标里的 SHA 已不在缓存中（仓库被淘汰后重新预热时上游已强推掉该提交），续读返回 `rev_not_found`。游标带版本字节，格式变更时旧版本游标返回 `invalid_argument`。

## Considered Options

- 服务端会话（游标为 ID，状态存内存）：重启即丢，占内存，还要过期回收；与无状态 MCP、单实例简单部署相冲突。排除。
- 游标只编码偏移、每次重新解析 rev：分支移动后续读会拼出来自两个提交的结果，违背"结果绑定解析提交"。排除。
- HMAC 签名游标：授权已每次重做，签名不增加安全性，只增加密钥管理。不采用。
